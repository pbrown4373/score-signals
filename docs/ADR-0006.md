# ADR 0006 — Tenant-scoped Brand Brain completion and maintenance

Status: Accepted

## Decision

Treat Brand Brain first-run setup as complete after a writer supplies a validated brand name, category, and description. Product, persona, voice, proof, and restriction fields remain available in the guided flow but may be skipped and maintained later.

Create the first Brand Brain through the authenticated, idempotent `bootstrap_brand_brain(jsonb)` database function. The function derives the user's first tenant membership, rejects VIEWER access, serializes concurrent attempts, and atomically creates every supplied entity. Later brands and all maintenance use tenant-scoped repositories over RLS-protected tables.

OWNER, ADMIN, and MEMBER roles may create, update, and delete Brand Brain records. VIEWER is read-only. Child records use composite `(tenant_id, brand_id)` foreign keys so a valid child cannot reference a brand in another tenant, even in privileged server contexts.

## Rationale

- The UX contract says optional details can be completed later, while the product still needs enough initial context to be useful.
- Atomic, replay-safe onboarding prevents double submissions and partial Brand Brain creation.
- MEMBER write access and VIEWER read-only behavior match the acceptance contract without requiring workspace administration privileges for normal product work.
- RLS protects browser access, while composite constraints preserve tenant invariants independently of the calling role.

## Consequences

- A tenant's first successful brand insert records `brand_brain_completed_at`; removing all brands does not erase the historical completion timestamp.
- Replaying first-run onboarding returns the existing first brand rather than creating a duplicate.
- Additional brands use the normal create flow after onboarding.
- The JSON onboarding input is an application boundary convenience; the function ignores unknown properties and relational constraints remain authoritative.
