# ADR 0005 — Claim-validated Supabase tenancy boundary

Status: Accepted

## Decision

Use Supabase Auth with cookie-backed SSR clients from `@supabase/ssr`. The Next.js proxy refreshes tokens, while protected server code authorizes only after `supabase.auth.getClaims()` validates the token.

Create a user's initial tenant through the authenticated `bootstrap_tenant(text)` database function. The function is security-definer, validates input, serializes concurrent calls with a transaction advisory lock, returns an existing membership when replayed, and creates an OWNER membership atomically when needed.

Keep membership lookup helpers in the non-exposed `private` schema. Enable RLS on tenants, profiles, and memberships; grant only the table operations required by each policy. OWNER and ADMIN may manage a tenant, VIEWER is read-only, and an OWNER cannot remove their own OWNER membership.

Verify policies with pgTAP against local Supabase/Postgres using authenticated JWT claim context.

## Rationale

- Cookie contents alone are not an authorization boundary.
- Atomic database bootstrap avoids partially created tenants and client-selected tenant authority.
- Security-definer helpers avoid recursive membership policies while retaining a small audited surface.
- Database-level policy tests exercise PostgreSQL behavior rather than duplicating policy logic in mocks.

## Consequences

- Local and CI verification require Docker and the Supabase CLI.
- The public Supabase URL and publishable key are required for auth routes; service-role credentials remain server/worker-only and are unused by browser flows.
- Membership-management UI is deferred, but its role and RLS contract is already enforced.
- Every later tenant-owned table must carry `tenant_id`, use membership-backed RLS, and add same-tenant relationship constraints where foreign keys alone are insufficient.
